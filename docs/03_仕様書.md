# デイリータスク管理アプリ 仕様書 Ver.1.8

作成日：2026-11-16
この文書は、本アプリの動作の正解を定める。要件の背景は「02_要件定義.md」、完成時の見た目は「04_完成予想図.md」を参照。

## 1. 対応OS・端末
- iOS 17以降、iPhone（縦画面前提）
- 技術：SwiftUI / SwiftData / UserNotifications / WidgetKit / Charts

## 2. 用語
| 用語 | 意味 |
|---|---|
| ゲーム日 | ゲームごとに、リセット時刻を境界とする1日の区切り。カレンダーの日付とは一致しないことがある |
| リセット時刻 | ゲームのデイリーが切り替わる時刻（例：5:00） |
| ウィークリー期間 | ウィークリーリセット（曜日＋時刻）から次回リセットまでの1週間 |
| 達成日 | そのゲームの有効なデイリータスクを全て完了したゲーム日 |
| ストリーク | 達成日が連続している日数（現在継続中＋最長を保持） |

## 3. データモデル（SwiftData）
### 3.1 Game（ゲーム）
| 項目 | 型 | 備考 |
|---|---|---|
| id | UUID | |
| name | String | ゲーム名（必須） |
| resetTime | 時刻（時・分） | デイリーリセット時刻。初期値 5:00 |
| weeklyResetWeekday | Int（1=日曜〜7=土曜） | ウィークリーリセット曜日。初期値 2（月曜） |
| weeklyResetTime | 時刻（時・分） | 初期値は resetTime と同じ。以後は連動しない（§3.4） |
| isActive | Bool | 初期値 true（有効）。休止中は今日の対象・通知・現在の集計から外す。過去の集計には影響しない（§8） |
| sortOrder | Int | 表示順 |
| note | String | 任意メモ |
| テーマカラーのパレット番号 | Int | 10色のパレットのインデックス。新規登録時は既存ゲーム数に応じてパレット順の色を提案し、保存前に変更できる。ライト／ダークの配色は完成予想図 §2.1 に従う |
| imageFileName | String? | ゲームの画像のファイル名。nil の場合は画像なし |

- 画像の実体は端末内のアプリ領域にファイルとして保存し、SwiftData にはファイル名だけを持つ（§3.5 と同じ方針）。外部送信や同期はしない。
- ゲームを削除する場合は、画像ファイルも併せて削除する。

### 3.2 TaskItem（タスク）
| 項目 | 型 | 備考 |
|---|---|---|
| id | UUID | |
| game | Gameへの参照 | |
| title | String | タスク名（必須） |
| kind | daily / weekly | 種別。初期値 daily |
| isEnabled | Bool | 初期値 true（有効）。無効タスクは対象から外す |
| sortOrder | Int | ゲーム内で一括の単一順序（daily／weekly混在）。無効タスクも含め、新規追加は末尾 |
| customResetWeekday | Int?（1=日曜〜7=土曜） | 個別リセットの曜日（weekly 用）。単独では使わない |
| customResetTime | 時刻（時・分）? | 個別リセットの時刻。nil の場合はゲームの設定に従う |

- 実効リセット設定：customResetTime が nil でない場合は、そのタスクは個別設定を持つ。daily は customResetTime を、weekly は customResetWeekday と customResetTime を、そのタスクのリセットとして使う。customResetTime が nil の場合はゲームの設定に従う（daily は Game.resetTime、weekly は Game.weeklyResetWeekday と Game.weeklyResetTime）。
- weekly で個別設定を持つ場合は、customResetWeekday と customResetTime の両方がそろっていることとする。
- 種別変更（daily⇔weekly）時は、§5.4 の完了記録の削除に加えて、個別設定も解除する（nil に戻す）。
- 既存のタスクは個別設定なし（nil）として扱い、挙動は変わらない。

### 3.3 CompletionRecord（完了記録）
| 項目 | 型 | 備考 |
|---|---|---|
| id | UUID | |
| task | TaskItemへの参照 | |
| periodKey | String | デイリー・ウィークリーともに、対象期間の開始時点の暦日（地方時、yyyy-MM-dd）。ウィークリーは日次リセット時刻に依存しない |
| completedAt | Date | 完了した実時刻 |

- 完了の有無は「その periodKey の記録が存在するか」で判定する。チェックを外したら記録を削除する。
- 過去の記録は履歴・統計のために保持する（自動削除しない）。
- 同一タスク・同一 periodKey の完了記録は1件のみとし、重複を作らない。実装時に保存前チェックとテストで担保する。
- タスクの名前変更などでは、過去の完了記録を再計算・変更しない。ただし、ゲーム削除・タスク単独削除・タスクの種別変更では、§5.4に従って該当する完了記録を削除する。
- タスクの変更が過去の達成集計に与える影響は §8 に従う。再計算そのものは完了記録を変更しない。無効化では記録を保持し、削除・種別変更では §5.4 に従って記録を削除する（2026-11-26 決定）。

### 3.4 入力条件・初期値の扱い
- ゲーム名・タスク名は必須とし、前後の空白を除いて判定し、空白のみは不可とする。同名は許可し、文字数上限は設けない。
- 週次リセット時刻の初期値は日次リセット時刻と同じとする。以後は連動せず、新規入力中・編集時に日次リセット時刻を変更しても週次リセット時刻は変わらない。

### 3.5 画像の記録（GameImageRecord）

| 項目 | 型 | 備考 |
|---|---|---|
| id | UUID | |
| game | Gameへの参照 | |
| periodKey | String | その日のデイリー期間の periodKey と同じ定義（対象期間の開始時点の暦日、地方時、yyyy-MM-dd） |
| createdAt | Date | 記録を作成した実時刻 |
| memo | String? | 短いメモ。任意 |
| imageFileNames | [String] | 画像ファイル名の配列。最大4件 |

- 画像の実体は端末内のアプリ領域にファイルとして保存し、SwiftData にはメタデータとファイル名だけを持つ。外部送信や同期はしない。
- 記録は「ゲーム」と「その日の期間」の両方に紐づく。実体は1か所に保存し、見せ方を2つ持つ（§5.6）。
- 保存時の縮小は、ゲーム画像（§3.1）は長辺 1024px、画像の記録は長辺 2048px を上限とする。アスペクト比を維持し、切り抜き（トリミング）はしない（2026-11-26 決定）。
- 同じゲーム・同じ日に複数の画像の記録を作れる（2026-11-26 決定）。
- ゲームを削除したときは、画像の記録と画像ファイルも、タスク・完了記録と一緒に削除する（§5.4、2026-11-26 決定）。

## 4. ゲーム日・期間の判定（最重要）
### 4.1 ゲーム日の求め方
- 現在のデイリーリセット設定で求めた境界（§4.4）のうち、現在時刻以前で最も新しい境界を期間の開始とする。期間はその境界から次の境界の直前までとする。
- ゲーム日とデイリーの periodKey は、期間開始時点の暦日（地方時、yyyy-MM-dd）とする。

例：R=5:00 のとき、11/17 4:30 は ゲーム日 11/16。11/17 5:00 は ゲーム日 11/17。

- タスクの期間は、タスクごとに、そのタスクの実効リセット設定（§3.2）で求める。境界と夏時間の扱いは従来どおり（§4.4）とする。
- ゲーム単位の集計などで使う「ゲーム日」は、ゲームの設定（既定値）から求める日次期間を指す。
- ストリーク・達成の集計（§8）の基準は、この「ゲーム日」とする。個別設定は各タスクの完了期間にだけ影響し、集計の区切りには使わない。集計ルールは §8 に確定内容を記載する（2026-11-26 決定）。

### 4.2 ウィークリー期間の求め方
- ウィークリーリセット（曜日 W・時刻 R）の境界（§4.4）のうち、現在時刻以前で最も新しい境界を期間の開始とする。期間はその境界から次の境界の直前までとし、periodKey はデイリーと同じく期間開始時点の暦日（地方時、yyyy-MM-dd）とする。デイリーのリセット時刻からは独立して決め、ゲーム日には変換しない（2026-11-16 本人決定）。
- 例：W=月曜・R=5:00 のとき、火曜4:00時点の期間開始は「前日の月曜5:00」であり、periodKey はその月曜のカレンダー日付。
- 例（デイリーとウィークリーの時刻がずれる場合）：デイリー5:00、W=月曜・R=4:00 のとき、期間開始は月曜4:00 で、periodKey はその月曜のカレンダー日付（例 "2026-11-16"）とする。その時点のゲーム日は前日（日曜）だが、periodKey には使わない。
- ウィークリータスクの期間は、そのタスクの実効リセット設定（§3.2）で求める。境界と夏時間の扱いは §4.4 に従う。

### 4.3 実装上の決まり
- 判定は `Packages/AppCore` 内の `GameDayCalculator` に集約し、画面・通知・ウィジェット・統計は必ずこれを使う（各所で別々に計算しない）。
- AppCoreはSwiftData・SwiftUIに依存しない純粋な計算層とする。SwiftDataのモデル（§3）はApp層に置き、Coreへはゲームの設定値や完了記録を通常の値として渡す。
- 境界ケースの単体テストを必須とする：リセット直前・直後、日付またぎ、週境界、月末・年末、うるう年（2/29）、夏時間の春の欠落時刻と秋の重複時刻。
- タイムゾーンは端末設定（現地時間）に従う。タイムゾーン変更時は、次回表示・判定から新しいゾーンで計算する（過去記録の periodKey は書き換えない）。

#### API契約（GameDayCalculator）
- `GameDayCalculator` はケースを持たない enum とし、判定は静的メソッドに集約する。
- 期間の取得は次のシグネチャで行う。

```swift
static func periods(
    now: Date,
    dailyReset: ResetTime,
    weeklyResetWeekday: Int,
    weeklyReset: ResetTime,
    calendar: Calendar,
    timeZone: TimeZone
) -> Periods?
```

- `ResetTime` はリセット時刻を表し、`hour: Int` と `minute: Int` を保持する。
- `Periods` は `daily: Period` と `weekly: Period` を保持する。
- `Period` は `start: Date`、`end: Date`、`key: String`（periodKey）を保持し、`Equatable` とする。期間は start を含み、end を含まない。
- 判定に使うタイムゾーンは引数 `timeZone` を正とし、`calendar` に適用して計算する。
- 戻り値が `nil` になる条件：日次・週次のどちらか一方でも、期間の開始・終了を求められない場合に `nil` を返す。具体的には、カレンダーの日付加減算で基準となるリセット対象日または隣のリセット対象日を取得できない場合、あるいは、いずれかの対象日の境界を取得できない場合に該当する。日の開始が境界にならず、カレンダーの時刻検索で候補が見つからないか候補が対象日と異なる場合は、その日の境界を取得できない。
- 入力の事前条件：`ResetTime` の `hour` は0〜23、`minute` は0〜59、`weeklyResetWeekday` は1〜7。範囲外は `precondition` 違反であり、`nil` を返す条件には含まれない。

タスク単位の期間は次のシグネチャで取得する。

```swift
static func period(
    now: Date,
    resetWeekday: Int?,
    reset: ResetTime,
    calendar: Calendar,
    timeZone: TimeZone
) -> Period?
```

- `resetWeekday` が nil の場合は日次（毎日）、1〜7 の場合はその曜日の週次として、現在時刻以前で最も新しい境界を期間の開始とし、次の境界を終了とする。
- 戻り値の `Period`（start・end・key）の定義、タイムゾーンの扱い、夏時間の境界の扱いは、既存の `periods(...)` と同じとする。
- 戻り値が `nil` になる条件は、対象の期間の開始・終了を求められない場合とし、既存の契約の考え方に合わせる。入力の事前条件（hour 0〜23、minute 0〜59、weekday 1〜7）も既存と同じとする。
- 既存の `periods(...)`（ゲーム単位で日次・週次を返す関数）は、ゲーム単位の表示・集計用に残し、その契約も §4.3 に維持する。タスクの期間計算には `period(...)` を使う（2026-11-26 決定）。

### 4.4 リセット境界と設定変更
- 各リセット対象日の境界は、その日の地方時が設定されたリセット時刻以上になる最初の瞬間とする。春の夏時間移行で指定時刻が存在しない場合はジャンプ直後、秋に同じ時刻が2回現れる場合は1回目を境界とする。夏時間移行によって期間は重ならず、逆行しない。
- リセット時刻の変更はデイリー・ウィークリーともに即時反映する。ゲーム日と週次期間は常に現在の設定で計算し、既存の完了記録は元の periodKey のまま保持する。表示する完了状態は現在の設定で求めた periodKey に従って移り、設定を戻せば表示も戻る。
- タスクの個別設定の変更・解除も、ゲームの設定変更と同じく即時反映とし、完了記録は変更しない。
- ゲームの設定変更は、個別設定のないタスクにだけ影響する。個別設定のあるタスクの期間は変わらない。

## 5. 画面仕様
画面構成と完成時の見た目は「04_完成予想図.md」を正とする。ここでは振る舞いを定める。

### 5.1 ホーム（今日）
- ゲームごとにグループ表示し、各タスクをチェック可能な行で並べる
- グループ見出しに「残り n 件／全 m 件」と、そのゲームのリセットまでの残り時間を表示する
- 全タスク完了のゲームは「完了」表示にして畳む（展開は可能）
- 日付表示はカレンダー日付と併せて、ゲーム日がずれるゲームには違和感のない表現にする（例：見出しは今日の日付で統一し、各ゲームのリセット時刻を明示）
- タスク行のタップで完了⇔未完了を切り替え、即座に保存・残数・ストリーク表示へ反映する
- ゲームカードの「次のリセット」は、そのゲームの有効なタスクの中で最も近い境界（タスクごとの実効リセット設定から計算したもの）を表示する。
- ゲームカードのヘッダーに、ゲームの画像がある場合はサムネイルを表示する（ゲーム名の横）。テーマカラーのドットは従来どおり併記し、画像が無い場合は従来どおりドットのみとする。
- ゲームカードは、ヘッダーのタップで手動で折りたためる。畳んだ状態ではタスク行を表示せず、ゲーム名・サムネイル・残り件数・次のリセットのみを表示し、カードの位置は変わらない。
- 開閉状態は端末内に保存し、アプリの再起動後も保持する。ただし、そのゲームの期間（日次・週次のいずれか）が切り替わったら、自動で開く。
- 完了したゲームの自動の折りたたみは、従来どおりこれとは別に動く。

### 5.2 ゲーム詳細
- そのゲームのタスク一覧（デイリー／ウィークリー）、現在のストリークと最長ストリーク
- 月カレンダー：達成日・一部完了日・未達成日を色分け表示
- ゲーム編集への導線
- 画像の記録（ギャラリー）への導線（§5.6）
- タスク行に、そのタスクの実効リセットを表示する（daily は時刻、weekly は曜日と時刻）。
- 個別設定中のタスクは、実効リセットの表示に「（個別）」を添えて、ゲームの設定に従うタスクと区別する（2026-11-26 決定）。例：デイリー · 23:59（個別）。

### 5.3 統計
- 週ごとの達成率（完了タスク数 ÷ 対象タスク数）を棒グラフで表示（Charts）
- ゲーム別フィルタを可能とする
- その日の記録：その日の画像の記録をゲームごとに表示する（§5.6）

### 5.4 ゲーム管理・タスク管理
- ゲームの追加・編集・削除、休止切替、並び替え
- タスクの追加・編集・削除、有効切替、並び替え
- 削除時は確認を表示する。ゲーム削除では配下のタスク・完了記録・画像の記録と、ゲーム画像・記録画像のファイルも削除する（§3.1・§3.5・§5.6）
- タスク単独削除時は、配下の完了記録も削除する。削除の確認表示に「完了記録も削除される」旨を含める
- タスクの種別変更（daily⇔weekly）時は、既存の完了記録を削除する。変更の確認表示にその旨を含める
- タスクの並び順はゲーム内で一括の単一順序とし、daily／weeklyを混在させる。無効タスクも順序に含め、新規タスクは末尾に追加する
- タスクの追加・編集に、リセット設定の項目を持つ。既定は「ゲームの設定に従う」とし、個別設定を選んだ場合は、そのタスクの種別に応じた入力欄（daily は時刻、weekly は曜日と時刻）を表示する。
- 個別設定の初期値は、その時点のゲームの設定とする。
- ゲームの追加・編集に、画像の項目を持つ。写真（PhotosPicker）から1枚を選べる。画像なしの状態にも戻せる。
- 保存時は長辺 1024px を上限に縮小する。アスペクト比は維持し、切り抜き（トリミング）はしない（2026-11-26 決定）。

### 5.5 設定
- 通知オン／オフ、通知リードタイム（分）の設定
- 通知権限が未許可の場合は、その旨と設定アプリへの案内を表示する

### 5.6 画像の記録（ギャラリー・追加）

- ギャラリー（完成予想図 07）
  - ゲーム詳細（§5.2）の導線から遷移する。そのゲームの画像の記録を、日付の新しい順に並べる。
  - 各記録には、日付・サムネイル（最大4枚）・メモ・その日のタスク達成状況を表示する。
  - 「画像を記録」ボタンで追加シートを開く。「戻る」でゲーム詳細へ戻る。
- 追加シート（完成予想図 08）
  - 紐づけ先のゲームは、表示中のゲームで固定する。対象の日は当日（その時点のゲーム日）に固定し、変更は許可しない（2026-11-26 決定）。
  - 写真の選択は PhotosPicker を使い、最大4枚まで。選択済みの枚数を表示する。
  - メモは任意入力とする。
  - 「保存」で記録を作成してギャラリーへ戻る。「キャンセル」では何も残さずに戻る。
- その日の記録（完成予想図 09）
  - 統計（§5.3）側の表示。その日の全ゲームの画像の記録を、ゲームごとに表示する。
  - ギャラリーと同じ記録を日付で絞った表示であり、データを2重に持たない。
  - 画像の記録が無いゲームは「画像の記録なし」と表示する。
- 記録やサムネイルのタップで拡大表示する（2026-11-26 決定）。
- 記録の削除は、ギャラリーで記録を開いて行う。削除時には確認ダイアログを表示する（2026-11-26 決定）。
- ゲームを削除したときは、画像の記録と画像ファイルも、タスク・完了記録と一緒に削除する（§3.5・§5.4、2026-11-26 決定）。

## 6. 通知仕様（UserNotifications・ローカル通知のみ）
- 対象：有効（isActive）なゲームのうち、そのゲーム日に未完了の有効デイリータスクが残っているもの（ウィークリーは締切当日＝リセット前日のゲーム日に限って対象に含める）
- 時刻：そのゲームのリセット時刻 − リードタイム（初期値60分）
- 内容：ゲーム名と残り件数（例：「◯◯：デイリーがあと2件残っています」）
- スケジュール方式：アプリ起動時・タスク状態変更時に、今後分を再計算して登録し直す（過去分・完了済み分は取り消す）
- 通知が許可されていない場合は登録を試みず、設定画面で案内する

## 7. ウィジェット仕様（WidgetKit）
- サイズ：small / medium に対応
- 表示：全ゲーム合計の残りタスク数、ゲーム別の残り件数（medium）、全完了時はその旨
- 更新：各ゲームのリセット時刻と、アプリ側の状態変更時にタイムラインを更新する
- タップでアプリのホームを開く
- データ共有は App Group 経由の SwiftData 共有ストアを使う

## 8. ストリーク・達成の計算
- 達成日の判定は「現在有効なデイリータスクが1件以上あり、全てにその期間の完了記録があること」で都度算出する（タスクが0件の日は達成日に数えない、2026-11-26 決定）。
- 現在ストリーク：直近のゲーム日から遡って達成日が連続している日数。ただし「今日（現在のゲーム日）」が未達成でも、まだリセット前ならストリークは切れていないものとして、昨日までの連続で表示する
- 最長ストリーク：過去の最大連続日数
- 計算は完了記録とタスク有効状態から都度算出する（ストリーク値そのものは保存しない）
- 再計算そのものは完了記録を変更しない。タスクの無効化では完了記録は残るが、判定の対象からは外れるため、過去の達成判定が変わり得る。タスクの削除と種別の変更では、既存のルール（§5.4 ほか）どおり、配下の完了記録も削除される。ゲームの休止は過去の集計に影響しない（2026-11-26 決定）。

## 9. エラー・不正状態への基本方針
- データが空（ゲーム未登録）の場合は、ホームに登録を促す案内を表示する
- 時刻・日付の計算で想定外の状態になった場合は、クラッシュさせず「未完了」側に倒す（やり忘れ防止が目的のため）
- 通知の登録に失敗しても、チェック機能など本体の動作は継続する
- 保存に失敗した場合は、エラーを表示し、画面を閉じずに入力内容を保持する

## 10. 完成条件
- §4の境界ケーステストが全て通過する
- 登録→チェック→リセット跨ぎ→通知→ウィジェットの流れが実機で確認できる
- 既存の登録データが、アプリ再起動後も保持される
