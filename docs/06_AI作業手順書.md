# デイリータスク管理アプリ AI作業手順書 Ver.1.0

作成日：2026-11-16
開発者本人が、AI（Codex等）と一緒に作業するときの手順。ルールの正本は「01_開発規約.md」。

## 1. この手順書について
- AIが出したコードは「未検証」が前提。到着したら必ず §6〜§7 の確認を通す。
- 作業は小さく区切る。1回の依頼は「1機能・1変更」まで。

## 2. 全体の流れ
```text
作業前の確認 → AIへ依頼 → コードを受け取る → コード検証
→ ビルド → Simulator確認 → 実機確認 → 正式採用 → GitHubへ保存 → 進捗記録を更新
```

## 3. 用語（やさしい説明）
- **正式コード**：検証を通して採用したコード。これが唯一の基準。
- **回帰確認**：新しい変更で、既存の機能が壊れていないか確かめること。
- **ゲーム日**：リセット時刻を境界とする、このアプリ独自の「1日」。

## 4. 作業の前にやること（毎回）
- [] 進捗記録（07）の「現在の状況」で、前回の続きと残件を確認する
- [] 今回やることをロードマップのフェーズと対応づける
- [] Gitの状態を確認する（作業ツリーがきれいか、今いるブランチはどこか）
- [] 必要なら作業ブランチを切る（例：`feature/phase2-gameday`）
- [] 関係する仕様書の節を読み返す（特に日付判定は仕様書 §4）

## 5. AIへの依頼の仕方
- 「AIへの依頼テンプレート.md」をコピーしてを埋めてから送る
- 必ず伝えること：
- 作業対象ファイルと、変更してよい／いけないファイル
- 現在の動作と期待する動作
- 関係する仕様（文書名と節番号）
- 完了条件
- コメントのルール（日本語、既存コメントを消さない）
- 依頼は曖昧にしない。「いい感じにして」ではなく、仕様の言葉で書く

## 6. AIの答えを受け取ったら
- [] 差分（diff）を全部見る。依頼していない変更が混ざっていないか
- [] 変更範囲が依頼と一致しているか
- [] 仕様と食い違う実装がないか（特に日付・時刻の判定方法）
- [] 既存のコメントが意図なく消えていないか
- [] 自分の言葉で変更内容を説明できるか。できなければAIに説明を求める
- 問題があれば、その場で大きく直さず、差分単位で指摘して直してもらう

## 7. ビルドと動作確認
- [] Xcodeでビルドが通る（エラー・警告を確認）
- [] AppCoreを変更した場合は `scripts/verify.sh` を実行し、単体テストの通過を確認する
- [] Simulatorで対象機能を確認する
- [] 既存機能の回帰確認（ホーム表示、チェック切替、保存）
- [] 日付判定に関わる変更は、単体テスト＋端末時刻をずらして境界を確認する
- [] 実機で対象機能を確認する（通知とウィジェットは実機必須）
- 確認結果は進捗記録へ。検証の段階（コード検証／Simulator／実機／正式採用）を分けて書く

## 8. うまくいかないときに戻す
- 直前の正式コード（直近のコミット）が戻し先。まず `git status` と差分で現状を把握する
- 原因が分かるまでは、戻した状態から最小の変更で再挑戦する
- 戻したこと自体も進捗記録に残す（何が起きて、どう戻したか）

## 9. GitHubへ保存する（コミットとプッシュ）
- コミットは「1機能・1変更」の単位で、内容が分かるメッセージを付ける
- 作業ブランチへプッシュし、完了条件を満たしたらPull Requestを作る
- `main` へ直接コミットしない

## 10. プルリクエストで確認する
- PRの説明に、AI変更報告（規約 §13）の内容を書く
- セルフレビューで差分を再読してからマージする

## 11. 困ったとき（早見表）
| 症状 | まず確認すること |
|---|---|
| ビルドエラー | エラー箇所の差分だけを見る。関係ないファイルまで直そうとしない |
| リセットで切り替わらない | GameDayCalculator の境界テスト結果と、端末の時刻・タイムゾーン |
| 通知が来ない | 通知権限、スケジュール登録のタイミング、対象ゲームの未完了有無 |
| ウィジェットが古いまま | App Groupの共有設定と、タイムライン更新の指定時刻 |
| データが消えた | モデル変更の有無。変更した場合は移行方法を仕様書に記録してから対処 |

## 12. やってはいけないこと
- AIのコードを未確認のまま `main` へ入れること
- 仕様書を更新せずに、仕様と違う実装を採用すること
- エラーを隠すための暫定処理を残したまま完了扱いにすること
- 一度に複数フェーズ分をまとめて実装させること

## 13. チェックリスト（1回の作業の締め）
- [] 差分を確認した
- [] ビルド・動作確認をした（段階を記録した）
- [] 回帰確認をした
- [] コミット／PRをした
- [] 進捗記録（07）を更新した
- [] AI変更報告を残した

## 14. AIに状況を伝えるとき
新しいセッションや別のAI（Claude等）へ引き継ぐときは、次を渡す：
- `AGENTS.md` と `docs/` 一式
- 現在のフェーズと、進捗記録の「現在の状況」
- 直近のAI変更報告と、未解決の残件

## 付録：コマンド早見表
```bash
git status # 作業ツリーとブランチの確認
git diff # 未保存の差分を見る
git checkout -b feature/xxx # 作業ブランチを作る
git add -A && git commit # 変更を保存する
git push -u origin feature/xxx # GitHubへ送る
```
